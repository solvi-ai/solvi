# Roadmap

What we plan to add or improve, roughly in priority order. Research items ship only if their pre-registered measurements
hold; the numbers are published either way (see the research notes linked from each release). Ideas and votes are welcome
in [Discussions → Ideas](https://github.com/solvi-ai/solvi/discussions/categories/ideas).

Status: `planned` · `in progress` · `research` (may not ship) · `done (version)`.

## Toward 1.0: what solvi is for, and everything that exists landed

First the goal and an honest account of what is there; the module cleanup and the split into two levels come after,
and follow from it.

| Item | What it gives | Status |
|---|---|---|
| **The goal and the mission, stated** | [docs/mission.md](docs/mission.md). solvi builds decision systems from fast solvers (rules, code, small models) and LLMs: the fast ones answer where they are sure, LLMs and search deliberate where they are not, a person decides what neither can; every decision is recorded, explainable and replayable. **Accountability and safety:** see how each model solves each task — what it read, who answered, what was promised, whether the promise held — and wrap any model in checks that keep it from doing harm. **Accumulated knowledge:** the system keeps verified knowledge about its environment — rules, action conditions, a world map, goals (an agenda with code done checks and gates); a written specification is compiled into rules, otherwise rules are learned from experience, each with its source, and every item can be checked and retracted. Knowledge protects by default (with its source and exact retraction); justified risk is an option that lowers the cost of protection without promising parity. Honest limits: growth was shown only in environments met again (a crafting game, the Pokémon world map), not on streams of one kind of decision (classification, matching) or for a support agent with tools, and the promise does not hold between an abrupt shift and its detection. **Any model**, including a small local one so much runs without the cloud (no quality promise for it). **Where to use:** single decisions (tickets, documents and contracts, policy decisions) and sequential decisions in an environment (agents with tools, planning, games). **What it is not:** a text generator, a hosted service or a replacement for LLMs; where a guarantee cannot be given it hands over to a person. **Honesty:** only what measurably helps enters the library, negative results are published next to positive ones, and a promise is a number you can check. | done |
| **Frequent decisions: a compact journal, budgets, outcomes as labels** | From a field report on 14 stands (a game loop wrote 14 KB a decision, 1.4 GB in an evening; model spend had no limit; outcomes the agent saw were not labels): compact records (`record="compact"` / `"sample:N"`, 2.0–5.2× smaller, still verified and replayed, what cannot be checked said as `not_kept`) and rotation of a JSONL store with linked segments; `Budget` / `Cost` on `solvi.core.slow.generate` and `solvi.core.slow.refine` (tokens, dollars, latency; stop by total or per decision; in the trace and the system report); `System.outcome` stores an outcome as a label for explicit recalibration; on-the-fly recalibration only in the experimental `solvi.experimental.oncalib`; full references of the refine loop and of `systemone`. | done (1.0, on dev) |
| **Everything that exists, landed** | Each module and feature in one of three places: works, with the measured value and the script behind the number; experimental, with what is missing; or removed. The README, the guide and the API reference follow that split. Removals done (CHANGELOG 1.0.0 "Removed"); `memory` and `episode` folded into the knowledge memory, `extract_multi` removed. | done (1.0, on dev) |

### Then, in 1.0: two levels and an experimental module

Built on the account above: what works becomes the stable low level, and the high level is put together from it.

| Item | What it gives | Status |
|---|---|---|
| Low level: building blocks with stable extension points | Runtime, parts, questions, storage and traces, guards, deciders, slow paths and dispatch as documented base classes and protocols you can subclass or replace, with a promise of which ones stay stable; your own pieces keep tracing, replay and guarantees; `solvi.core` exports every extension point, `solvi.testing.conformance` checks yours ([Building blocks](docs/building_blocks.md)) | done (1.0, on dev) |
| High level: ready-made systems | A System 1 + System 2 system in one, where you choose the models and providers and state what you need (questions, examples, risk, budget); built only from the low level, so any piece can be swapped out. `solvi.build` and `solvi.Guard`; `solvi.Knowledge` (store, agenda, action model, failure memory in one object; `build(knowledge=)`, `Guard(knowledge=)`) and `solvi.Agent` (an environment agent: System 1 on what the knowledge predicts, System 2 a search, hard checks from gates and refusals, protection by default and `RiskBudget` as an option, every decision replayable; example 25). Next: the agent on a real game environment with a measured run before any claim beyond the toy | in progress (on `dev`) |
| Clear split in docs and imports | A short path for the high level; a reference for the low level: the docs in three parts (Using solvi, Building blocks, Experimental), the API reference by level, `solvi migrate` for the new import paths | done (1.0, on dev) |
| `solvi.experimental` | Pieces that work but are not yet measured well enough for the stable promise live in one submodule, with what they still need to graduate (`solvi.experimental.STATUS`, [docs/experimental.md](docs/experimental.md)); graduate or go by 1.2 | done (1.0, on dev) |

## Library: open items from earlier releases

| Item | What it gives | Status |
|---|---|---|
| **Several questions per pass by default** | The decider answers many questions about one state in one forward pass (≈2–3× faster). Trained with a consistency loss, the answers still differ from one-question-per-pass in ~3–10% of cases on real states, so it stays off; next: an architecture where questions are independent queries over a text encoded once. | research |
| **Which record changed: a trace signature** | `solvi.core.store.signature`: 64 bytes kept next to the head; when a stored record was edited and every hash after it and the head recomputed, `verify(signature=...)` names the record and restores its content hash (`candidates=` finds the original in a backup). A syndrome code (two sums mod a 256-bit prime); the positional octonion code, kept for future tree-shaped (derivation) signatures, left the package in 0.8 for `benchmarks/octonion_signature.py`. One changed record: 2000/2000 located, 0 wrong; several: detected, not located. | preview (0.7) |
| **`solvi serve`: HTTP and MCP server** | `solvi serve catalog.py:system` exposes the questions as an HTTP API (FastAPI, OpenAPI schema from the same pydantic types) and as an MCP server (each question a tool), and a decider behind the System One API (`POST /v1/systemone`); traces go to TraceStorage — done for 0.6. Guarding an agent's tool calls (`solvi.solutions.guard.Guard`: the agent proposes a call, solvi checks it — catalog, types, grounding in the conversation, instruction-like tool outputs, policies, an authorizer under act_guard and perturb — and makes it, denies it or escalates it, every decision a stored trace), and an MCP proxy (`solvi serve --guard --upstream`) — done for 0.7 (adapters for PydanticAI, LangGraph and the OpenAI Agents SDK came too, and were removed in 1.0: no measured run went through them); hardened before release: approvals bound to the call and the reasons shown, `scan_user` for pasted injections, `locale=` for ambiguous numbers. Measured on AgentDojo (97 tasks, two open models): default settings cut successful attacks by 93–97% but blocked honest tasks that take payees or recipients from tool outputs (67% → 51%, 84% → 56% solved). Added for 0.7, opt-in: `tool_values="escalate"` (such a value goes to a person instead of a refusal), a `"url"` matcher, `require_request` policies for actions with no user-given value, and a wider detector of booking / event / visit commands. All together with a reviewer: attacks 0.6% / 1.6%, honest tasks 72% / 75%, a person asked in 28–31% of honest tasks. Next: measure the new detector rules and intents on attacks they were not written for; a reviewer UI that shows the injected instruction next to the escalated value. | done (0.6); agent guard: preview (0.7); framework adapters removed (1.0); MCP proxy with a guard: stable in `solvi.serve` (1.1, measured against the real filesystem server) |
| **Verifiable specialists** | Small models for one job each, under one contract (`solvi.core.specialist`, stable in 1.1: every run a record of kind "specialist" in the decisions' store, replayed from it): the model proposes a typed spec, code checks it against the source, code renders it, the trace replays to identical bytes; what does not verify is marked, never invented. Measured with a corruption test (`solvi.testing.corrupt` in 1.1: corrupted proposals, the share the check catches). First: **verified charts** (`solvi.experimental.charts`) — every number on the chart quoted from the text, with its unit and scale; a deterministic, accessible SVG. Next: tables and slides (the same checks, HTML / PPTX output), then checking layers over open speech models (speech to text: silence has no words, forced alignment, a term dictionary; text to speech: numbers and dates normalised by rules, the synthesised audio transcribed back and compared). | contract: stable (1.1), runs on the core store; charts: preview (0.7); tables, slides, speech: planned |
| **Explaining a decision: the smallest change that flips it** | `solvi.core.explain`: for a decision, the smallest change of its given inputs that changes the answer — adverse-action reasons for regulated decisions (lending, insurance) and clear answers in support — found by re-running the deterministic flow with model parts held at their recorded proposals. Measured on the credit policy (`benchmarks/counterfactual_credit.py`): every explanation valid on re-decision, thresholds minimal against brute force, one or two fields for nearly every refused application; the cost of a change is the caller's (`text_cost=`, `costs=`). Next: costs learned from what people accept as an explanation. | experimental (0.7); stable (1.1) |
| **Gallery: helpers for coding agents** | Three runnable entries for decisions a coding agent meets on every task: a pre-edit rule check (rules per path glob; code checks where code can, a decider's question per fuzzy rule under act_guard and perturb; allow / block / escalate), review triage (seven risk questions, quick review only for a confident "no" to all, P(a risky change goes to quick review) ≤ 10%), a skill picker with an honest "none" (ties escalate with their candidates). Offline with keyword stand-ins and synthetic labels. Next: calibrate solvi-large and an LLM decider on labelled real edits, changes and prompts, and publish what the promise costs in escalations. | done (0.7.1); calibration on real edits: planned |
| **Laws of an environment from experience** | `solvi.experimental.laws`: a wrong prediction proposes candidate laws over a grammar of atoms you write; a candidate is accepted only by a held-out test on other worlds, sessions or paths (support, precision, net error reduction), applied most specific first, retired when its held-out precision falls, written into the knowledge store with the transitions it was accepted on; a probe planner for live systems (read-only before write). Measured on two stands: on a game simulator with written mechanics 94% of the gap between a learned map and the written mechanics closed, random candidates under the same test within 1.1 points (the test does the work); on a real MCP filesystem server with a path policy, refusals 6 → 0 in one session against 48 → 29 with random probes; two toys reproduce both in `benchmarks/laws_toy.py`. Limits: the live probe-based learner can admit false laws on policies the grammar cannot express (observed once per control policy) — admission by probes or sized acceptance is the open item. Next: a grammar too large to enumerate (where the mismatch should matter), retirement of weak laws nothing contradicts, wiring into `solvi.Agent`. | experimental (1.1, on `dev`) |
| **Learning in a world described by code** | `solvi.experimental.skills`: where the world is code, System 2 plans on an exact model (a copy of the environment; the real one is never stepped by the planner), a plan counts only after the code re-simulated it, verified plans are compiled into System 1 skills over a grammar of atoms, and a skill acts alone only while its outcomes keep an anytime-valid certificate (System 2 re-verifies it at every use before that; an alarm on its alone outcomes retires it); `as_s2` gives `solvi.Agent` planning on an exact model; skills go into the knowledge store with their plan, start and simulation hash. Measured on a deterministic gridworld (`benchmarks/skills_toy.py`, 20 fresh layouts × 5 seeds): System 1's share 0 → 0.81 with every goal reached, 1.5% of its decisions in failed runs under a 20% promise pooled over the skills; cases never transferred, unverified plans reached no goal. Measured on Crafter (version 1.8.3; written mechanics as the exact model; symbolic state; hand-written survival reflexes shared by every arm, 60% of all steps; the planner reads the copy's full map while the game shows an agent a 9×7 window), in one run of 10 streams × 30 episodes, no agent seed (the loop is deterministic given the world seeds). Achievements are unique achievements unlocked per episode (of 22). The skill set was certified at 5% / δ 0.1 (fifty clean uses, one e-process pooled over the stream's skills) in every stream by episode 1–2. In the last ten episodes System 1 acted alone 1,350 times with an observed outcome and failed twice (0.15%, Wilson upper bound 0.54%; 4 of 2,882 over the whole run); 57 further alone runs were paused by a reflex and not resumed, so they carry no outcome (counted as failures they would make 4.2%, Wilson 5.4%). The promise is the set's, not a single skill's; a skill's own alarm retires it (4 retirements, each later re-certified). Goals that are stochastic by the written rules stayed with System 2 and are outside the promise. With skills the planner was called 32 times per episode against 42 when it plans every goal (−23%), and an episode took 84 s against 107 s on the same machine (−21%), with achievements kept: 15.2 against 15.7 unique achievements unlocked per episode of 22 (ratio 0.966, bootstrap lower bound 0.934). System 1's share of the non-reflex steps rose from 7% in the first ten episodes to 23% in the last ten (9% of all steps); the pre-registered bar of 60% was missed. Routes to a resource and plans for unseen footprints stay System 2 by design (routes were 25% of non-reflex steps), and every certified skill was a one- or two-step gather sequence with a constant footprint: in an open world the planner did most of the work and skills took the repeatable part. Hierarchical skills and conditions with variables are untested. An arm that executed and compiled random action sequences of the plan's length in place of verified plans unlocked 4.0 unique achievements per episode against 13.7 for the same agent with no memory at all; none of its 5,497 unverified skills was ever certified, so System 1 never acted. The gain is the verified plans', not the loop's bookkeeping, and the certificate held unverified skills out; what unverified memory does on its own was not measured. The observation-only learner (the agent's own action memory with the written gates on) unlocked 13.3 unique achievements per episode, no higher than the same agent without memory (13.7); the planner arms' lead over both is the planner's with the full map. The planner reads the whole map of the copy; a Crafter agent sees a 9×7 window from pixels. No number here is comparable with published Crafter scores (a geometric mean of success rates over 1M training steps). Open: hierarchical skills, footprints with variables, a world where observation is expensive, a service with a specification, a condition rule that specialises after a failure, a planner with a heuristic. | experimental (1.1, on `dev`) |
| **Relational rules: enumerate, test, compile** | `solvi.experimental.relations`: a state as relations over its nodes (a path tree, a grid seen from the player); a relation-algebra enumerator keeps one program per behaviour (full relations over the examples, hashed) and ranks them by the precision of a readout; `RelAlgProposer` hands them to the laws' held-out test as atoms; a `Library` makes accepted programs terminals; a found rule runs as plain set code or index arrays after a pair-for-pair check, and a law set compiles into one module checked row for row (`LawSet.to_module`, `check_compiled`). Measured (`benchmarks/relations_battery.py`, `benchmarks/relations_compile.py`): 22 of 28 pre-registered random rules found within seven nodes, all exact on larger graphs of other families, a 4-clique rule never accepted; closure, grandparent and sibling on a forest of 100,000 nodes equal pair for pair; the index-array backend within 0.7–1.3× of hand code over a parent array (output conversion excluded); the plain set-code backend 2–3× slower than hand-written set code over the same pairs; a law set learned on the toy grid compiled with 0 differences on 100,000 rows. On five law sets learned on a game simulator with written mechanics (61–103 laws each; one with 64 relational atoms over a 3×3 window compiled as a bounded domain), `LawSet.to_module` + `check_compiled` agreed with `LawSet.predict` on every one of 308,510 logged transitions (training, validation and test worlds), no atom refused. A differential check on logged rows certifies the module on those rows, not equivalence in general — run it on your own rows. The compiled law part ran ≈ 14× (flat atoms) and ≈ 120–165× (64 relational atoms) faster than the library's own row-by-row interpreter on 100,000 rows (single runs; the interpreter evaluates every atom of the grammar per row, the compiled module only the atoms of each law's condition and stops at the first hit). That is a speedup over the interpreter, not over hand-written code: on a forest of 100,000 nodes the index-array backend was within 0.7–1.3× of hand code over a parent array, and the set-code backend 2–3× slower than hand-written set code over the same pairs. Measured on the stands named earlier as next: relational atoms (an ancestor directory named secret) were measured once on an MCP filesystem server behind a written guard and on a game simulator with written mechanics: on the server they removed the refusals under a secret directory the flat grammar made, but one unrelated refusal remained, so the pre-registered bar of zero refusals was missed; on the game simulator +0.02 points; one layout, one run each (the full sentence in the best practices, relational rules). Limits: compiled relation programs are not faster than hand-written set code on graphs (2–3× slower). Next: the search depth with twenty-odd relations, dropping proposed atoms no law uses (composite rules through the library: the next row). | experimental (1.1, on `dev`) |
| **Rules over relations: composites with a library** | `solvi.experimental.relations.library`: `find_rules` enumerates small programs over the relations of a state (a path tree, a family forest) bottom-up with observational equivalence, admits only what passes a held-out test on other worlds, and builds the next rules on the admitted ones as new terminals; a fallback slot for a learned proposer (none ships). Measured on two toys (`benchmarks/relations_library_toy.py`, five seeds): every level of a three-level path rule and of a kinship ladder to depth 6 found within 2,556 / 10,817 enumerated programs, where flat search found neither top rule in 100,000; 0 false accepts; the kinship ladder misses its bar of a tenth of the flat budget (1.08×), the universal relation U enlarging every level; with U left out of the terminals (`include_universal=False`, opt-in) it costs 7,889 and meets it. On a synthetic five-level path-tree policy (denied if an ancestor directory is named secret and the depth is at least three; the four intermediate relations given as named, unordered targets) `find_rules` with the library found every level within 4,111–4,132 enumerated programs over five seeds; without the library the top level was not found within the cap of 1,000,000 programs, so the budget ratio is at most 0.0042 and its true value unknown. Per level the library is not free (90 vs 71 and 2,951 vs 1,898 programs on two of the shared levels; cheaper only on one). Two controls — a rule no program of the grammar can express, and one that needs a 56-node program — were never admitted (0 of 20 runs). On the kinship ladder (nine rungs up to second cousin once removed) the library found all nine within 3,370–3,378 programs; without it eight of nine — the ninth needs a program of at least 17 nodes where the no-library search exhausted size 15 at ≈ 500,000 programs. 0 false accepts on held-out forests of the same generator at a larger size. Next: a file server's path policy and a game simulator's cells as stands, intermediate concepts the search proposes itself. | experimental (1.1, on `dev`) |
| **Composition tables: rules learned by counting, refusal where they cannot derive** | `solvi.experimental.relations.CompositionTable`: which relation two relations compose to, counted exactly from labelled chains (majority ≥ 0.9, support ≥ 2), empty cells filled by residuals from chains of three, a long chain derived over every bracketing and answered only when the bracketings agree, otherwise refused with the reason; the cells used are the answer's reason and go into the knowledge store as rules; an admission hook with the laws' sized acceptance and a base-rate null. No model is involved: the table is learned by counting and the derivation is code. Measured on CLUTRR (Sinha et al., 2019), the clean split trained on chains of 2–3 relations and tested on 2–10; the input is the benchmark's relation graph — the chain of relations between the two people — not the story text; the text-to-graph step is not part of this measurement: a table learned by counting (majority 0.9, support 2, residual fill, all bracketings must agree; 111 cells from 9,074 training chains of length 2–3 in 0.07 s on CPU) gave 0 wrong among 1,087 answered of 1,146 test queries (38–190 per length; at lengths 2 and 3 only 2 and 7 distinct chains): precision among the answered 1.000 (0 of 1,087) at every length 2–10, coverage 0.949 overall, 0.975 at length 10 (116 of 119) and 0.916–0.993 at lengths 4–9; 59 refused (21 disagreeing bracketings, 38 underivable); one split, one run; the most frequent training relation per length answered 0.077 (0.134 at length 10); the benchmark is generated by closed-path composition rules, so an exact table can exist by construction; what is measured is whether counting with refusal recovers it without errors. Limits: the sized acceptance with a base-rate null admits an exact 2-vote cell only for a relation with base rate ≤ 0.03 — on a 10% slice it refused 12 of 15 exact support-2 cells the default admits; keep `support=` explicit for deterministic tables (a null of exactness is not built); residual fill after a different table admits different cells and was the source of that arm's extra wrong answers (residual votes are not gated like direct votes); one relation per cell, so a gender-dependent cell is refused, not split (no gender slot), and the opt-in identity relation, with no gender slot, gave 9 wrong answers at lengths 4–10. Forward chaining to a fixed point over the learned rules in the knowledge store (`relations.forward_chain`): derived facts with their premises and the rule as their justification, never above the weaker premise, two derived relations of one pair a dispute, retraction and promotion followed without a re-run; measured on CLUTRR (Sinha et al., 2019), the clean split's training file only (the relation graph of each story, not its text): on 1,816 held-out stories (a fifth of the training file by a hash of the id, chains of 2 and 3 relations; the table fitted on the other four fifths, 111 cells) the store's reading of the query pair after chaining to the fixed point was compared with the table's derivation over the shortest paths: 1,675 equal (0.922), 11 disputed where the bracketings disagree (0.006), 130 with nothing derived where the table cannot derive (0.072), 0 differences; the fixed point took 0 rounds for 72 stories, 1 for 826 and 2 for 918; 2.6 s of chaining in all, 1.4 ms a story, on CPU; one run, the test file not read. On 120 random chains of 2–7 relations over 12 random tables whose bracketings can disagree: 0 differences (2 answers equal to the table's rest only on a disputed pair and stay hypotheses until a person answers it); limits: composition rules over pair facts only. Next: gender-dependent cells (a gender slot), the text setting (story → relation graph with a specialist and checking code), a null of exactness for deterministic tables, residual votes gated like direct votes. | experimental (1.1, on `dev`) |
| **Rules first, a model second** | `solvi.experimental.relations.RulesFirst`: the composition table answers what it derives and no model is called; what it refuses goes to a fallback (a decider or an LLM) with the question rendered from the chains and the options, or stays a refusal; every answer names its path, is journal-ready and replays from its record without the model. ## Strategist

| Item | What it gives | Status |
|---|---|---|
| **Reliability-aware producer choice** | Choose among producers by how often each one is accepted and right, learned from outcomes (continues the learned producer policy). | planned |
| **Text in: entry points** | Text → which question is asked + its typed input state: the decider picks the entry point, spans and deterministic parsers fill the fields with quotes; provenance says the input was read by a model. `system.ask_text`, `solvi.core.textin.TextIn`, dialogue updates; served as `POST /ask_text` and an MCP tool. Next: measure the share of wrong actions that pass the checks on gallery catalogs, and a generative fallback only where a parser fails. | done (0.7) |
| **Learning from corrections, with gates and rollback** | The system learns from every human correction of an escalation, every known outcome and every proposal your rules rejected — never from its own accepted answers (tried three times: no gain). By the number of labels per process: shift/scale (today's `fit` / `teach`), a memory of corrected cases and a small head, then a LoRA adapter (`solvi.experimental.lora.adapt_lora`, experimental in 0.7; not yet wired into the ladder). Every update runs in shadow, is diffed against the current one, must beat it on held-out labels and pass the honesty suite, recalibrates `act_guard` on fresh labels, and is recorded in each trace so it can be rolled back. The scaffold shipped in 0.7 as experimental and off by default (the learning loop: trusted labels only, the ladder, the gates, versions and rollback, tested with stand-in models); in 1.1 the loop is removed (no measurable gain on streams of one kind of decision) and its ladder and gates are the update target of the change pipeline (`Change(artifact="update")`, `LearningTarget`). **Measured 2026-10 on two stands as one change pipeline for three sources (a document version, a person's corrections, a person's labels on a stream), every candidate through the same stages and one hash-chained journal:** on a credit policy the pipeline carried a new version with 144 of 144 changed decisions traced to their clause, admitted 12 of 12 exact exceptions, held every widening one for a person and refused 8 of 8 exceptions that would have touched other applications (0 extraneous changes; 14 versions replayed without a failure); on a bank-request stream with 20 new topics, a person's labels on escalated requests recalibrated the guarantee and refitted the head every 200 requests under the promise (≤ 5% wrong among the answers given alone, kept in both halves), but answered only 0.9 points more alone: labels taken from escalations are the hard cases and tighten the threshold, and the new topics reached the head (70 options) without passing it — and no stage refused any of the 22 candidates, so the gates added nothing there. Decision: the pipeline is journal, impact analysis and rollback infrastructure (`solvi.experimental.changes` in 1.1; see the measured paragraph), not a learning claim. **Follow-up (2026-10):** the same stream with seven kinds of labels for a fixed System 1 — escalations, random audits, both with sampling weights, an active policy with an anytime-valid certificate — kept the promise in every arm and raised the share answered alone by at most 1.4 points; the weights changed no decision, a group threshold for the new topics never certified (≈ 180 clean labels per group needed, 174 given), the certificate never reached its bound at 10% or 30% labels. Labels on a stream do not raise coverage for a fixed answerer; growth needs new answerers and hundreds of labels per new option. | loop removed in 1.1; a labelled update is a candidate change of the pipeline (experimental, infrastructure) |
| **Models read, compiled rules decide** | For decisions under a policy or regulation: the model fills typed facts (a quote checked against the text, or "not stated"), the rules are code — compiled from the document and checked before use — and the decision is that code run on the facts; a missing fact → "cannot compute" and escalation; a judgement stays the model's, marked as such. Measured first with an LLM on a stream of cases under two versions of a regulation: the mode where the model writes the computation itself (an operation and pointers to its operands, executed by code) replayed exactly but was no more accurate than the model's direct answer, so it is dropped; the split where the model only reads the facts and hand-written rule code decides held (consistent with SARA-style results) — an upper bound until the cases are real claims. Measured next on 118 real court decisions under an air-passenger regulation: a fact schema compiled from the regulation's own text fits about half of the cases (the hand-made schema fitted none); on the cases the rules decide, rules compiled by the model are wrong in about half and hand-written rules with a verbatim quote per rule in about a third — both below the bar — because half of the disputes carry none of the regulation's quantities and most of the rest turn on an open term ("extraordinary circumstances"). Decision: the rules are written by a person, one quote per rule; the model only reads facts; a rule that meets an open term returns "cannot compute" naming the term and the case escalates to a person or a model, marked as such. Next for the library: the rule interpreter with quotes and the "open term" outcome beside "missing fact". Accuracy numbers only on template cases, with this boundary stated. | research |
| **Knowledge compiler: a new document version changes behaviour** | A new version of a policy or regulation becomes a candidate change of knowledge, rules and checks: what changed (a fact, a rule, or the meaning of a term), which rules and past decisions depend on it, a replay of those decisions, and promotion only with a person's approval; validity dates, so the trace says why a decision on one date differs from another. Measured: compiling the rules from the document without a person matched the reference on the regulation the model already knew but did not carry to a new one, and choosing among several compiled versions picked worse than the best single version; the impact analysis of a patch (which past decisions change, with the clause behind each) held on an unseen text. So the rules are compiled by a person and the change pipeline — patch, impact analysis, replay of both versions, boundary tests — stays as infrastructure, with no novelty claim for the compiler itself. | research |
| **Gated evolution of behaviour** | Measured and not shipped. A change proposed by an LLM or by mutation (reflex parameters, rules as code), scored against the current system on fresh worlds and confirmed on others before promotion, was run on a crafting game: growth stayed below the pre-registered bar, an LLM proposed no better than random mutation, and the gate's benefit was not statistically established; a memory of verified rescues and hazard rules induced from them did no better than random rules with the same actions. What held: knowledge about the environment (action preconditions, a map) carried across episodes, and search over exact rules. So the library does not learn behaviour; it accumulates rules and facts under a gate — the change pipeline stays as infrastructure (candidate, journal, gates, approval levels, rollback), and behaviour is a planner over rules and knowledge. | measured, dropped |
| **Learned environment dynamics for search** | Measured and not shipped. A symbolic model of a crafting game's dynamics, learned from the agent's own logs (ordered probabilistic rule lists per event class, a spawn hazard, a memory of enemies out of view), served as the simulator for System 2 search at pre-death states and in live episodes. Live, it beat a scripted escape (+37 steps per episode, lower bound +23) — but a hand-written model of the same mechanics did exactly as well, and search on the exact dynamics without knowledge of the future random draws did better still (+79); the remaining gap to an oracle that knows those draws is the world's randomness, not model error, and both models were equally over-confident about the plan they chose. So the library does not learn environment dynamics: where an environment has written rules (a simulator, a specification, a model of its mechanics as an `Environment`), System 2 is a search over them that picks the plan by the lower bound of its survival over several rollouts; where it has none, System 2 is an LLM or a person. | measured, dropped |
